# Lifewave App — Pre-Build Audit (Phase 2)

*Standing rule (AGENTS.md, 2026-10-15): run before building — permissions, null-safety/error handling, API misuse, protocol contracts, security, dependency/version check. Written 2026-10-17 against `SPEC.md` §7 (Phase 2) before M1 scaffolding. Refresh at every milestone gate (M1–M5); a stale audit does not clear a build. Companion file: `CHANGE-IMPACT-AUDIT.md`. Package-existence verification was done by pub.dev web search on 2026-10-17; anything not confirmed there is marked (unverified).*

## 1. Permissions — every sensitive API call matched to its permission

Rule: a permission is requested **at first use of its feature, in context, with a plain-language explanation and a typed fallback** — never all-up-front at first launch, never without a denial path.

| API / capability planned | Android permission (manifest) | Windows equivalent | Requested when | If denied |
|---|---|---|---|---|
| Native STT (`speech_to_text`) — chat dictation, interpreter turns, ask-the-guide, roleplay | `RECORD_AUDIO` + `<queries>` declaration for `android.speech.RecognitionService` (required since Android 11 or the recognizer silently reports unavailable) | OS microphone privacy permission; Windows speech recognition availability varies (see §3) | First tap on any mic button | Mic buttons switch to "type instead"; all features remain fully usable by typing |
| Audio playback — Kokoro path / `flutter_tts` fallback, interpreter output | None (playback needs no permission; audio-focus handling is code, not permission) | None | — | — |
| Internet (`http`) — cloud escalation, asset downloads (Kokoro model, language packs), updater check, future user-connected social accounts | `INTERNET` | No declaration needed; user firewall rules apply | Declared in manifest (normal permission, no runtime prompt) | Offline mode: bundled DB + downloaded packs keep working; cloud features show "needs internet" plainly |
| Local notifications (`flutter_local_notifications`) — profile-queue post reminders, follow-up/reorder reminders, one-time update notice | `POST_NOTIFICATIONS` (runtime, Android 13+); `SCHEDULE_EXACT_ALARM` **only if** a reminder truly needs exact timing (see §3 — prefer inexact) | None (in-app surfacing; no toast integration in v1) | First time the user sets a reminder or the updater finds a version | Reminders fall back to in-app badges on the Today card; update notice shows in-app only |
| Sharing fact cards / QR one-pager (`share_plus`), opening links (`url_launcher`) | None (system share sheet / intent; FileProvider for shared files — no storage permission) | None | — | — |
| Printing quick-start / QR one-pager | None (system print flow) | System print dialog | — | Save-as-file via share sheet instead |
| Per-user storage (`path_provider` + app-private files; `shared_preferences` for small settings) | None — app-private internal storage needs no permission. **No broad storage permission (`READ/WRITE_EXTERNAL_STORAGE`, `MANAGE_EXTERNAL_STORAGE`) — ever** | Per-user app data dir under the per-user install | — | — |
| Home-screen mic widget (Android) | None beyond the mic permission above (widget is a launcher surface) | n/a | When the user adds the widget | Widget absent; in-app mic unchanged |

**Explicitly NOT requested in v1:** contacts, location (any), camera (QR is generated, not scanned), Bluetooth (conversation mode uses the *system's existing* audio routing — no `BLUETOOTH_CONNECT` scan/pair APIs are called; if implementation ever calls them, this audit must be re-run first), SMS/phone state, accessibility, overlay, install-packages (the updater hands off to the system installer / GitHub release page; it does not self-install APKs).

**Windows note:** the `Setup.exe` is per-user with no admin requirement (standing Windows rule). Any build step that produces an installer demanding elevation fails this audit.

## 2. Null-safety / error handling (Dart rules for this app)

Dart is null-safe by language design; these rules are about *data-shaped* nulls, which the type system cannot see because the DB and all network payloads arrive as decoded JSON.

- **DB entries:** decode through one checked factory per entry type. Required fields (`id`, `topic`, `title`, `body`, `audience`, `source_type`, `source_ref`, `claim_label`, `updated` — SPEC §5) missing or mistyped ⇒ the **entry is skipped and counted** in diagnostics, never partially rendered. Optional fields (`price_retail_usd`, `price_subscribe_usd`, `item_code`, `category`) missing ⇒ UI renders **"not listed"** — never crash, never invent a value, never carry a price over from a sibling entry.
- **Manifest:** unparseable manifest, missing `db_version`, or a topic listed in the manifest with no file ⇒ DB load fails *closed* to the last-known-good bundle (or, on first run, to a plain "database didn't load — here's what to try" screen logged in diagnostics). The chat layer never runs against a half-loaded DB.
- **Retrieval/chat:** zero retrieved entries ⇒ the assistant says it doesn't have that in the database and offers the cloud-escalation path (if configured) — it does **not** answer from model memory about products/prices. Claim labels travel with the entry object through answer assembly; an answer fragment without a label is a bug, caught by unit test (CHANGE-IMPACT-AUDIT §9).
- **Network (cloud escalation, downloads, updater):** every call has a timeout, a typed failure (offline / timeout / HTTP status / bad payload), and a user-visible plain-language outcome. No uncaught `Future` errors; no silent retries forever — the interpreter/translation cascades use bounded attempts with the timeout-cascade pattern (SPEC §7.5) and always land on a usable fallback (on-device result, text mode, or device TTS).
- **Platform channels (STT/TTS/notifications):** every channel call is wrapped — `MissingPluginException` / platform error ⇒ feature degrades (typing, silent text display, in-app badge) and the failure is written to the diagnostics card with the feature name. A voice failure must never take down chat.
- **Per-user stores:** reads of pipeline/journey/preferences tolerate missing keys (first-run defaults), corrupt JSON (preserve-but-ignore + diagnostics entry, per CHANGE-IMPACT-AUDIT §4 — never wipe), and version skew.
- **Generated content:** post/reply/fact-card generation that fails compliance checking is **blocked with the flagged text shown to the user**, never auto-rewritten silently in a loop and never sent. Empty generation ⇒ say so and offer a template.

## 3. API misuse risks

- **Flutter platform channels — STT (`speech_to_text`):** initialize once and reuse the instance; `listen()` only after successful `initialize()`; handle `onStatus`/`onError` (permanent vs transient) instead of assuming a session is live. Android 11+ package-visibility: without the `<queries>` block for the recognition service (§1), STT reports "unavailable" with no error — the classic silent failure. **Windows:** desktop speech recognition support is the weak platform — the Windows build must feature-detect STT and present typing + push-to-talk-via-system-dictation honestly rather than promising parity (guide states per-platform reality).
- **TTS (`flutter_tts`) + Kokoro path:** `flutter_tts` is the *fallback* renderer, not the primary (§7.3). Misuse risks: fire-and-forget `speak()` with no completion/error handler (the Scout mid-sentence cut-off class of bug) — all playback goes through one speech controller that tracks utterance completion, interruption (new utterance, call, audio-focus loss), and surfaces state to diagnostics. Do not hold a wakelock for playback. Kokoro runs through its own inference bridge; if that bridge is a platform channel, the same once-only init + typed-error rules apply, and a missing/un-downloaded model is a *normal state*, never an exception path.
- **Background scheduling on Android:** there is **no background service and no wake word** in v1. Reminders are local notifications scheduled with the OS. Android 12+ restricts exact alarms (`SCHEDULE_EXACT_ALARM` is denied by default on Android 13+ for new installs and Play policy restricts it further); post-time reminders are *nudges*, so schedule them **inexact** (or with the reminder window stated honestly — "around 9:00") rather than requesting exact-alarm capability the app doesn't need. Doze/battery-optimization can delay inexact notifications — the Today card is the source of truth, notifications are best-effort copies. Do not add `workmanager`-style periodic jobs for the updater: the updater checks on app open (standing rule), not on a background timer.
- **Page-vs-profile scheduling reality (Meta platform):** true scheduled publishing exists only for Facebook **Pages** via the platform API; **personal-profile posts cannot be scheduled by third-party apps at all** — no API, no workaround, and any library/SDK claiming otherwise is misrepresenting the platform. The app implements exactly SPEC §7.1: Page ⇒ (future, via the user's own connection) scheduled publish; profile ⇒ local queue + timed reminder + one-tap post via share flow. Cross-posting (Instagram/Threads, §7.8 item 8) has the same shape: each platform's API has its own account-type and review requirements; nothing in v1 may present a queued cross-post as a sent one.
- **Share sheet (`share_plus`):** a completed share-sheet handoff means "handed to the target app," not "posted." State labels must reflect that (§7.11 honesty rule).
- **Translation engines:** on-device packs are per-language downloads with their own availability list (~59 languages) — the UI must query actual pack/device support at runtime (STT/TTS locale lists come from the device, not a hard-coded marketing list) and fall back to text mode where speech is unsupported (§7.5).

## 4. Protocol contracts

- **Knowledge DB contract:** `db/manifest.json` is the index — fields `app`, `db_version` (integer, monotonic), `counts`, `files[]` (`topic`, `path`, `entries`), `queued_topics`, `rules`. Entry schema per SPEC §5 (required/optional fields, `source_type` and `claim_label` enums, `audience` always `"public"`). Contract rules: the app reads topics **from the manifest**, tolerates missing/queued topics and older `db_version`s, accepts an update bundle only if it parses fully, validates, and is newer (CHANGE-IMPACT-AUDIT §4), and never writes to the bundled DB. Any schema change requires a `db_version` bump + a HARVEST-LOG/SPEC note in the same commit — no silent schema drift.
- **Updater contract — GitHub repo `smartyourtv/lifewave-app`:** the repo root carries `version.json` (same pattern as Scout's updater): it must contain, per platform, the latest `versionCode` (Android, integer, monotonic) / version string (Windows), the release tag, and the download asset name. The app: fetches `version.json`, compares integers (never string-compare versions), and if newer, shows **one** subtle notification for that version (dismissed ⇒ not repeated until the next version), with an update button that opens the GitHub Release asset — user taps to install; never forced, never silent. Asset naming: stable filenames (`Lifewave-latest.apk`, `Lifewave-Setup.exe`) under `releases/latest/download/` so links never rot. A malformed/missing `version.json` ⇒ updater reports "couldn't check for updates" in diagnostics and tries again next launch — never blocks the app.
- **Cloud escalation contract (generic cloud only — never van Scout, SPEC §7.7):** request = `{ question, retrieved_entries: [{id, title, body, claim_label, source_ref}], ui_language }`; response = `{ answer_text, cited_entry_ids: [...], model_notice }`. Rules: the cloud tier answers **grounded in the supplied entries**; `cited_entry_ids` must be a subset of the sent ids (anything else is discarded and the answer is downgraded to on-device-only); claim labels in the answer derive from the cited entries, never from the model; no per-user data (journal, pipeline, names) is ever included in a request; requests carry no builder credential (§5). The interface is defined in M1 even though the live tier may land later, so chat code never grows a second, ad-hoc network path.
- **Internal contracts:** diagnostics card exposes DB version, Kokoro model state (absent/downloading/ready + size), per-language pack state, STT/TTS availability per platform, and last updater check result — these states are enums shared by Settings, diagnostics, and the guide, defined once.

## 5. Security

- **No exposed tokens/secrets:** the shipped app contains **no API keys, tokens, or credentials** — verified at M5 by grepping the built bundle/pubspec assets for key-shaped strings (part of the SPEC §8 release checks). There is no builder-owned cloud secret; see CHANGE-IMPACT-AUDIT §5, red flag 1.
- **User-supplied cloud config (if the user adds their own API key):** entered only in Settings, stored only in platform secure storage (Android Keystore / Windows DPAPI-backed store via a secure-storage plugin — package marked (unverified) in §6 until confirmed), used only as the auth header on that user's escalation requests, **never** logged, never shown in diagnostics (diagnostics may show "cloud: configured / not configured" only), never included in any share/export, and removable in one tap. Keys are never written to `shared_preferences` or plain files.
- **User data stays on-device:** preferences, rename, "remember that…" notes, pipeline, journey journal, drafts, and the user's referral link live in app-private storage; journal/pipeline stores use the platform's encrypted-at-rest file protection, and any future export is an explicit user-initiated share-sheet action. No analytics, no telemetry, no third-party trackers (§ CHANGE-IMPACT-AUDIT §5). The only outbound traffic is: updater check (GitHub), asset downloads (GitHub/CDN), cloud escalation (only the question + public DB entries, §4), and user-initiated shares.
- **Facebook/social:** no Facebook SDK, no embedded login webview, no credential handling in v1. A future user-connection flow must be OAuth in the system browser with tokens in secure storage — and it triggers a re-run of this audit (§1/§5) before it ships.
- **Content security:** outbound text (posts/replies/fact cards/translations) passes the compliance checker before queueing; claim labels cannot be stripped by translation (§7.4 final-language check). Pointer entries render as pointers everywhere, including in generated content — the generator may reference a pointer ("covered in the group's guides") but may not expand it.
- **Supply chain:** dependencies pinned (§6); no packages from git URLs or unknown publishers in v1; `pubspec.lock` committed so builds are reproducible.

- **Maintenance rule:** any package unmaintained > ~18 months, or requiring a Flutter/AGP bump on its own, needs a named fallback in this file before it becomes load-bearing. Single-point-of-failure features and their fallbacks: STT (`speech_to_text` → typing is the fallback), TTS (`flutter_tts` is itself the fallback for Kokoro), notifications (`flutter_local_notifications` → Today-card badges), sharing (`share_plus` → save-image + `url_launcher` flows).

## Red flags found by this audit

1. **`share_plus` latest vs pinned Flutter 3.24.5 conflict** (§6) — must be resolved explicitly at pubspec time; the most likely silent build-breaker in the list.
2. **Android exact-alarm temptation** (§3) — post reminders do not justify `SCHEDULE_EXACT_ALARM`; inexact + Today card is the design.
3. **Windows STT parity** (§3) — desktop speech support is materially weaker than Android; the spec/guide must not promise identical voice input on PC.
4. **Two (unverified) packages** (§6) — `qr_flutter` and the secure-storage/printing options were not confirmed in this pass's searches; they gate M4/M2 work items, not M1.
